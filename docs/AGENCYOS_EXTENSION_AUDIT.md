## Current stack and ownership

The existing application uses Next.js 15, React 19, TypeScript, passkey/session authentication, private Vercel Blob records and conditional writes. Existing account IDs own client workspaces and project IDs. The current checkout has no Prisma ORM or organization-membership tables. Owner identity is restricted to the designated studio owner; each current client has one authenticated account. UI styling uses the existing KJL studio components.

Adaptive discovery is implemented in `/start-project`, `/studio/inquiries` and their APIs. Reviewed discovery can create or link an existing client project. `/portal` and `/studio` provide project updates, messages/reviews and payment requests. The first delivery increment adds `/portal/delivery`, `/studio/delivery`, `/api/portal/delivery`, type-specific onboarding, explicit owner review/scheduling, activity and retry receipts.

Contracts/business work exists in separate active worktrees, including a checkout currently integrating it. Its authenticated `/api/portal/business` interface supplies accepted proposals, executed agreements, invoice/payment gates and sandbox mode. Its database and provider layer remain owned there. Software care is separately committed at `69bf2e0`, including subscriptions, requests, estimates, payment-confirmed allowances and recorded work. Preserve both. This extension does not replace their billing records or create competing time/allowance calculations.

## Additive persistence and migration

Extend each existing `DeliveryProject` with optional approver, milestones, immutable published versions, immutable review decisions and revision tasks. Add optional held outbox entries to `DeliveryState`. Missing fields default to empty; existing records need no rewrite or backfill. Artifact paths are generated by the server under the existing private namespace. Artifacts are written before their manifest is committed; a failed manifest save may leave an inaccessible orphan. Retain and reconcile such objects, never delete them on an ambiguous write result. The manifest, decision, revision task, audit and outbox event commit atomically via the existing CAS transaction.

No price, subscription, payment, contract or legacy project phase field is changed. Rollback removes the new UI/routes while preserving delivery aggregates, evidence and private files. A future database migration must preserve original IDs, hashes, reviews and operation receipts and run copy/count/hash checks in a separate integration effort.

## Authorized UX for the next increment

1. Owner explicitly designates the existing client account as approver; revocation is always available.
2. After the onboarding/schedule/start gate, the owner creates a milestone with real acceptance criteria and an optional actual due date.
3. Owner uploads a bounded PDF, PNG, JPEG, WebP or text artifact, confirms its scope alignment, and publishes immutable V1. Its private bytes, checksum, source scope and publisher are recorded.
4. The designated authenticated client downloads the exact file and approves or requests changes to the latest reviewable version. A stale version, revoked approver, cross-client access or repeated conflicting decision is rejected.
5. Requested changes create one linked revision task. Owner classifies it against the signed scope. Additional scope creates an internal draft requiring the existing commercial amendment process. Publishing against a changed baseline requires explicit owner confirmation and re-established onboarding/start readiness.
6. New versions preserve all previous files and decisions. Publishing V2 makes V1 unreviewable. The action center shows review/revision work independently of the ongoing delivery stage.

## Prioritized risks and limits

1. **Commercial integration:** final contracts API and real sandbox provider chain remain unverified here. Fail closed on missing/revoked readiness or changed scope; do not manufacture provider evidence.
2. **Approval authority:** no team/membership migration is assumed. Approval is only for the explicitly selected existing client account, checked again at decision time. Staff cannot approve on its behalf.
3. **Artifact safety:** owner-only uploads, strict size/type checks, immutable private storage, forced downloads and integrity checks. No antivirus provider is available; do not describe files as malware-scanned. Executable/HTML/SVG/archive uploads are excluded.
4. **Concurrency:** conditional manifest writes and operation digests prevent stale publication/approval and duplicate revision/outbox records. Preserve bytes after uncertain writes for recovery.
5. **Scope:** feedback is never a charge authorization. A scope-change draft is internal decision support, not a signed amendment or automatic invoice.
6. **Scale:** the current bounded Blob aggregates and 100-client roster are appropriate for this incremental workflow, not proof of capacity for 50 concurrent active clients. Pagination, indexes and load tests precede that claim.

## Five-PR release sequence

1. **Onboarding/action center — already built (`3ae4690`).** Connect to final contracts implementation; verify real sandbox proposal/signature/deposit chain. Existing authorization, replay and browser checks are retained.
2. **Deliverables/approvals — implement now.** Private immutable artifacts, designated approver, exact-version decisions, revision triage, scope-change drafts and held outbox. Tests include stale V1 after V2, revoked/foreign/owner actors, duplicate decisions, corrupted/private files, changed scope, and desktop/phone workflow.
3. **Care usage and change-order integration.** Reuse care ledger and business amendments; actual billing periods, eligible time, approved estimates and explicit additional quotes. Validate boundary, legacy plan, renewal and plan-change behavior.
4. **Economics/capacity.** Reconcile provider payments/refunds, distinct invoiced/collected/recognized amounts, direct costs, real work minutes, owner availability and buffer. Never turn a capacity suggestion into an accepted commitment.
5. **Notifications/handoff.** Verified event inbox and durable outbox dispatch, approved reminder policy, authorized client updates, ownership handoff and retention. Sending and live financial actions remain disabled until authorized.

Each increment must carry its own working UI, negative authorization tests, appropriate regression/build checks, rollback and explicit deferred scope. QA uses synthetic commercial fixtures until the actual combined provider integration is ready; it cannot stand in for a signed agreement or payment.
